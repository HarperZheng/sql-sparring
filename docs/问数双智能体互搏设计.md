# 问数双智能体互搏（总体设计）

> 2026-10-21 立项。目标：让 datus 与 cube 两个问数智能体对同一批自然语言问题独立作答、互相检查、裁决出正确/修正答案，并把分歧按回改五步落到各自的语义层建模，形成"出题→互答→互检→裁决→回改→复验"的持续闭环。
>
> **v0 已人工跑通首轮**：同 25 题（q01-q25）双链路同日实测 + 逐题对账，见 datus 仓库 `development_process_record/non_tax/` 下：09-datus-票据链路问数实测记录、09-cube-票据链路问数实测记录、10-票据链路问数对账（datus-vs-cube）。本文档将该实践固化为可重复的机制设计；实施设计（角色组件化/考纲出题/适配器固化/里程碑）见 [implementation.md](implementation.md)。

---

## 一、总体设计

### 1.1 目标与定位

- **表面目标**：每道题评出正确答案或修正答案。
- **真正目标**：通过分歧暴露**两套语义层的建模差距**（缺指标、口径不一致、维度/时间轴缺失、名不副实），按回改流程修模，拍板口径逐轮沉淀进**课本「已裁定口径」章节与 conf/metrics.json 指标登记表**。
- 两个智能体的语义层建模对象与风格完全不同（datus=dosi 语义模型 YAML，16 指标/7 数据集，资金链为主；cube=Cube schema + 场景词典，票据链为主）——**这不是障碍，是互搏的价值来源**：同一业务概念在两套语义层里的表达差异，正是人工建模时最容易自洽而看不见的盲区。

### 1.2 已核实前提

| 前提 | 结论 | 依据 |
|---|---|---|
| 底层数据是否同源 | **同库**：双方都查 ClickHouse `172.18.166.126:8123/yunnan0508` | datus `conf/agent.yml`；cube `.env`（Oracle yn0411 为旧源，仅保留连接） |
| 数值互证是否成立 | 成立（同库同数据；同脏同噪声，比对公平） | 10 号对账文档 q05/q10/q13/q16/q18 完全一致即为实证 |
| 双方调用面是否可脚本化 | 均可（见本文二、三） | datus `POST :8501/api/v1/chat/stream` SSE 流；`POST :4100/chat` 三态 JSON |

### 1.3 角色拓扑

```

                    │  出题人（第三方 Claude）  │
                    │  读考纲出题（盲考）       │
                    └───────────┬─────────────┘
              题目分发（双方互相不可见）
        ┌──────────────────┴──────────────────┐
        ▼                                     ▼
┌──────────────────┐                ┌──────────────────┐
│ datus 答题人      │                │ cube 答题人       │
│ :8501 chat API    │                │ POST :4100/chat   │
│ 语义层: fne_fund_ │                │ 语义层: Cube      │
│ main.yml (资金链) │                │ schema (票据链)   │
└────────┬─────────┘                └────────┬─────────┘
         └──────────┬────────────────────────┘
                    ▼
         ┌─────────────────────┐
         │ 裁判（第三方 Claude） │ ← 同时读两侧语义层定义
         │ 口径对齐 → 数值比对   │
         └──────────┬──────────┘
                    ▼
      verdict（裁决书）→ report.md（轮报）→〔系统终点〕｜回改五步（人调起智能体+人）：查证起草（建 feedback.md）→审定→施工→复验→闭环
```

**角色隔离原则**：出题人、裁判不属于任何一方；裁判只看双方产出 + 两侧语义层定义，不看对方答题过程；答题双方独立会话、互不可见对方答案。

### 1.4 核心机制：三层比对（语义层不同，禁止直接比答案文本）

直接拿两个 narrative 答案让 LLM 判"哪个对"会得出垃圾结论。首轮对账（10 号文档）也证明：25 题中多数差异是**口径差异而非对错差异**。必须先结构化：

**Step 1 提取作答卡**。每个答案结构化为**值行**数组（指标×维度成员→一个数+单位，D14；口径自述不落卡——D10，可从 SQL 追溯）：

```json
"values": [
  {"metric": "缴款金额", "unit": "元", "dims": {"执收单位": "A单位"}, "value": 18208936572.27}
]
```

**Step 2 按口径分类，而不是按值分类**：

| 情形 | 判定 | 互搏含义 |
|---|---|---|
| 口径不同（值同或异） | **建模差异**，不是谁错 | 进口径对齐表，是互搏的首要产出 |
| 口径相同 + 值相同 | 互证通过 | 警惕假一致：同库同脏 + 口径巧合（如直缴口径恰等于全口径），靠 Step 1 拦截 |
| 口径相同 + 值不同 | 执行层事故 | 查 SQL/query/结果行/错误码，定位 SQL bug 或语义层 expression 错 |

**Step 3 三级基准裁决**：

- **T1 有文档基准**（07 号清单基准、09-cube 实测记录拍板、P0 对数、yoy.baseline）→ 硬对基准；
- **T2 无基准**：双方口径对齐且值一致 → 互证通过；
- **T3 分歧**：裁判产出**修正答案**（取对的一方 + 口径说明），人工确认后随回改⑤闭环沉淀（feedback.md 行状态=闭环）。
- 对账注记纪律（沿用 10 号文档）：**只陈述双方数字与口径的客观差异，不预判哪方正确**；涉及业务口径取舍（如欠缴定义）进"口径分歧清单"人工拍板，拍板后双边同步修。

### 1.5 语义层差异的专门处理

1. **出题以考纲为源，不以答题人能力为源**：考官按"课本"出题——课本=业务知识（业务链路、术语、层级、已裁定口径），源资料为业务方文档（`syllabus/bussiness/`，决策 D11），**不读答题人侧任何产出、不读数据项与数据源**（盲考，双侧对称）。按答题人现有能力出题会把考卷锚死在答题人现状上，永远发现不了"双侧都没建模"的缺口——v0 的 q26-q30 为反证：预期 nomatch 的 3 题实际可答，这类缺口只有从业务出发才问得出来；问到库中无数据的内容撞出 nomatch，正是"双侧共同缺口"的发现方式。**题型只保留问数族**（定义详见 `examiner/SKILL.md`，配比由调用方按轮给定，缺省问数族 5 型各 6 = 30 题；概念族 4 型与环节归因本期撤销，见文末 §五）：
   - **问数族**（考数据查询，答案形态必须是**数值、排名、清单、分布**之一）：**总量趋势**（汇总数与时间趋势）、**排名对比**（按业务维度的 TopN/对比/占比，维度取自课本：执收单位/缴款人/收入项目/科目/区划清分归属/代理银行与账户/直缴汇缴）、**分布结构**（分桶与结构占比）、**超期账龄**（欠缴/超期/账龄区间）、**异常校验**（环节顺序倒挂、重复、状态与资金矛盾）。
2. **口径对齐表是第一产出物**：`{业务概念 | datus 建模 | cube 建模 | 是否一致 | 拍板}`。首轮已暴露典型行：欠缴（datus: state='1'+feffdate 过期 vs 清单原建议 is_received='0'）、划拨（批次头行重复计数陷阱）、缴库时间轴（msg_date vs fill_date 族）、笔数去重键（fid vs fpaycode）。
3. **裁判输入=两侧作答卡**：四态判定只靠两卡（sql 文本 + metrics_hit + 值行已足够，SQL 里去重键/时间轴一眼可见；散文不落卡，D14）；仅 nomatch 归因时现查语义层相关定义（datus=YAML、cube=词典）。
4. **独有口径不强判对错**，人工拍板后写回对齐表，下一轮变成 T1 基准。

### 1.6 闭环：回改五步（查证起草 → 审定 → 施工 → 复验 → 闭环）

**不自动回改（用户拍板）**：round.py 出**轮报**（report.md）即到系统段终点；回改单不是系统产物——**回改①由人看过轮报分歧明细后调起智能体**，codeqa 逐题查真实字段解法（过滤器+指标+维度+时间锚），由智能体创建 `rounds/<轮>/feedback.md` 回改单（文件头契约+主表+回改卡）。此后按**回改五步**走（不叫回灌）：

| 步 | 谁 | 做什么 | 状态流转 | 产出物 |
|---|---|---|---|---|
| ① 查证起草 | 智能体（人调起） | 读轮报分歧明细，用 codeqa 逐题查真实字段解法（过滤器+指标+维度+时间锚），创建回改单 | 待查证→草案 | feedback.md（新建）：各行拍板结论+回改卡 |
| ② 审定 | 人 | 逐行审定拍板结论与双侧改法 | 草案→已审定 | — |
| ③ 施工 | 人 | 按回改卡改双侧语义层（cube 拍板口径落词典属施工） | 已审定→已施工 | 语义层 diff |
| ④ 复验 | 系统 | `bin/round.py --retest` 一条命令自动：清 datus chat memory（全量，不可逆无备份，用户拍板 2026-10-26）→重启两服务→复验集=上轮分歧∩非剔除行、原题原 ID 重跑→裁决关口→轮报 | 已施工→（挂：回③；口径错：回①） | 新轮完整记录 |
| ⑤ 闭环 | 人 | 复验通过且人工确认后置 feedback.md 行状态=闭环（无独立套件文件——feedback.md 即闭环账本） | 已施工→闭环 | feedback.md 状态列 |

冲突规则：回改单与裁决书冲突以回改单为准（回改单产生于 codeqa 查证之后）；回改单与课本「已裁定口径」冲突以课本为准（课本是下一轮出题依据）。按建模对象归类的修法参照：

| 问题类型 | datus 修法 | cube 修法 |
|---|---|---|
| 口径错误 | metric expression / ai_context 改 YAML | schema measure 改 + 词典回写（`POST /agent/dictionary`） |
| 缺指标/缺维度 | fne_fund_main.yml 补指标（dosi 建模流程） | schema 加 member |
| 名不副实（检索不中） | KB 描述/ai_context 改写 | 词典/场景描述改写 |
| 执行 bug | ch_compat/引擎问题单 | cube-patch 问题单 |

**复验与闭环（回改④⑤）**：④由 `bin/round.py --retest` 一条命令自动——清 datus chat memory（全量，不可逆无备份，用户拍板 2026-10-26）→重启两服务→复验集=上轮分歧∩非剔除行、原题原 ID 重跑到轮报；挂了回③、口径错回①。⑤通过且**人工确认**后，人把 feedback.md 行状态改"闭环"——feedback.md 即闭环账本（无独立套件文件），闭环拍板口径沉淀指标登记表 `conf/metrics.json`。每轮轮报四指标：一致率（值行两级判定 D14）、分歧分布、差距数（双侧共同缺口）、闭环率（跨轮指标：上轮分歧题在本轮复验集的通过率）——曲线收敛即语义层在人工驾驭下被优化。

### 1.7 记录层：每道题记在哪、什么格式

存储按"**原始留痕 → 机器提取 → 裁决 → 回改闭环**"四层组织，每层只服务于一个用途，禁止混写：

```
D:\develop\sql-sparring\
  syllabus\{bussiness\,business.md}      考纲=原始资料+业务课本（出题唯一依据，D11）
  rounds\round-01\
    questions.jsonl                     题库：每行一题
    runs\datus\qNN.payload.jsonl        原始 payload 流（datus，chat API SSE 解出的 MessagePayload）+ qNN.meta.json（会话/耗时/token）
    runs\cube\qNN.raw.json              原始 /chat 响应 + agent-svc 日志摘录
    answers\datus\qNN.json              机器提取层：作答记录（含工具级命中指标）
    answers\cube\qNN.json
    verdicts\qNN.json                   裁决书：双侧口径卡 + 对照 + 判词 + 修正答案
    feedback.md                         回改单（回改①产物，人看过轮报后由智能体创建：文件头+主表+回改卡）；行状态=闭环即闭环账本（无独立套件文件）
    report.md                           轮报（由 questions+answers+verdicts 渲染）
```

**① questions.jsonl**（每行一题，JSON Lines）：

```json
{"id":"q01","round":"round-01","question":"2022年全年非税缴款金额和笔数是多少？",
 "category":"收入","type":"总量趋势",
 "syllabus_ref":["B10","B20"],
 "baseline":{"source":"07号清单 q01","note":"原基准标注疑误，见10号对账"}}
```

字段：`type` 为题型（问数族 5 型，见 §1.5）；`syllabus_ref` 回指课本知识点编号（出题人据此做覆盖矩阵，漏项打回补题）；**题库不含预期断言**——"谁该会"由实答揭示，nomatch 本身即登记；`baseline` 是可选 T1 基准。机器题库必带 `type/syllabus_ref`（`bin/examine.py` 逐行校验）；M0 手写题库仅 `id/question/source`，契约同样接受（schemas/question.schema.json）。

**② answers/&lt;side&gt;/qNN.json**（机器提取层，每题每方一份，两侧同构）：

```json
{
  "id": "q01",
  "question": "2022年全年非税缴款金额和笔数是多少？",
  "status": "answer|ask|nomatch|timeout|error|failed",
  "elapsed_s": 116.0,
  "metrics_hit": [
    {"tool": "query_metrics", "names": ["非税缴款金额", "非税缴款笔数"],
     "params": {"time_start": "2022-01-01", "time_end": "2023-01-01"},
     "rows": "index,非税缴款金额,非税缴款笔数\n0,18208936572.27,355"}
  ],
  "sql": "SELECT sum(famt) ...", "sql_count": 3,
  "values": [
    {"metric": "缴款金额", "unit": "元", "value": 18208936572.27},
    {"metric": "缴款笔数", "unit": "笔", "value": 355}
  ],
  "errors": [],
  "arbiter": null,
  "raw_path": "runs/datus/q01.payload.jsonl"
}
```

- **工具级命中指标记在本层 `metrics_hit`**（datus 形态 `{tool,depth,names}`、cube 形态 `{measures,dimensions}`）——直接可从 datus payload 流与 cube /chat 响应解析产出，无需 LLM 参与。
- 两侧 `status` 共用**六值枚举**（M1 拍板 D10）：`answer/ask/nomatch/timeout/error/failed`——`failed`=适配器链路失败（连不上服务），`error`=智能体答错/中断，`timeout`=超时截断；cube 反问与拍板全程记录在 `arbiter`。
- `sql` 双侧同放 SQL 文本（cube 为 :4000 编译后），`sql_count`=执行条数；**口径卡不在本层，只在裁决书 `cards`**（D10）。
- **值行为答案唯一载体（D14，round-02 起生效）**：`values` 每行=指标×维度成员→数+单位；`metric` 取指标登记表（`conf/metrics.json`），无则标 `未登记:<名>`；`dims` ≤2 个键值对（总量行省略）；`value` 为数字或 null（禁字符串数字）；`unit` 枚举 元/万元/亿元/笔/张/个/天/%；`note` 放一句话限定语。**只登记原始计量**——合计/占比/排名属导出量，由代码从原始行导出比对。提取步由适配器内置（`adapters/value_extract.py`，模型走 `conf/models.json` extractor 节）把答案散文结构化为值行（只抄数不推算），散文本身不落卡、全文在 `runs/` 留痕（`raw_path` 指认）；`answer` 字段已自契约删除（2026-10-26 拍板）；round-02 卡已迁移为值行（`bin/migrate_cards_values.py`，数字源=裁决书口径卡）；m0 存档卡文件里的 answer 原样保留（D10 不改写不迁移），校验豁免、schema 不再描述。

**③ verdicts/qNN.json**（裁决书，每题一份，跨双方）：

```json
{
  "id": "q01",
  "round": "round-NN",
  "cards": {
    "datus": {"metric": "缴款金额+笔数", "caliber": "SUM(famt) / COUNT(DISTINCT fid)，全业务类型",
              "dimensions": "按月分组", "time_window": "fill_date ∈ [2022, 2023)", "values": {"金额": 18208936572.27, "笔数": 355}},
    "cube":  {"metric": "缴款金额+笔数", "caliber": "SUM(famt) / COUNT(DISTINCT fpaycode)，全业务类型",
              "dimensions": "按月分组", "time_window": "ffilldate ∈ [2022, 2023)", "values": {"金额": 18208936572.27, "笔数": 334}}
  },
  "comparison": {"metrics": [
      {"name": "金额", "caliber_same": true,  "value_same": true,  "note": ""},
      {"name": "笔数", "caliber_same": false, "value_same": false, "note": "去重键 fid vs fpaycode"}],
   "summary": "数值一致系两套口径恰好覆盖同批明细，判建模差异"},
  "verdict": "建模差异|互证通过|执行事故|待人工",
  "verdict_detail": [{"side": "cube", "type": "改口径", "target": "笔数去重键", "suggest": "统一去重键或双侧各注口径"}],
  "corrected": null,
  "evidence_refs": ["rounds/round-NN/answers/datus/q01.json", "rounds/round-NN/answers/cube/q01.json"]
}
```

- **口径级指标对照记在本层 `cards` + `comparison`**——由裁判从两侧作答卡值行 + sql + 语义层定义归一产出，这是"指标"的第二级记录（业务口径级，可跨语义层比较）；**口径卡只在本层**（M1 拍板 D10），作答卡不设。
- `comparison.metrics` 每指标一行先比口径后比数值（D4），轮报一致率/分歧分布从这里机器统计；`verdict_detail` 数组（0..n 条问题单）即回改问题单的机器形态，回改①的智能体据它起草回改单主表与回改卡（D12：side 支持 both，type 四分 补指标/补维度/改口径/修bug——补建模与修bug 分开记）；T3 分歧的修正答案在 `corrected`，人工确认后随回改⑤闭环沉淀；`evidence_refs` 只引双侧作答卡（runs 留痕不入 git，也不入引用）。

**④ feedback.md 闭环行**（闭环账本，跨轮累积；无独立套件文件——用户拍板 2026-10-26）：

复验通过且人工确认后，人把该题行状态改"闭环"；闭环行的拍板口径（真实字段解法：过滤器+指标+维度+时间锚）沉淀进指标登记表 `conf/metrics.json`（metrics/key_aliases 两节），供下一轮值行判定与适配器引用。

两级指标的区别总结：`answers` 层的 `metrics_hit` 回答"**agent 用了哪些指标算的**"（过程证据）；`verdicts` 层的 `cards` 回答"**双方口径各是什么、值是否可比**"（裁决证据）。语义层不同使得同名指标可能口径不同、同口径可能异名——两级缺一不可。

**v1 数据来源**：M0 起的活跑留痕（rounds/*/runs/）即 ①，作答卡即 ②；10 号对账总表的每行"对照关系"即 ③ 的雏形，v1 由裁决流程升格为结构化 verdicts。首轮实测与对账文档留在 datus 仓作叙事记录，机器层 v1 起落 sparring 工作区。

### 1.8 风险与对策（首轮实测教训直接适用）

| 风险 | 实证 | 对策 |
|---|---|---|
| 记忆污染 | datus 批跑中 agent 援引/回写 `.datus/memory` 旧口径（"沿用 q10 拍板"），cube ask 拍板也回写词典 | 回改施工时**先清旧拍板再写新拍板**；互搏轮内禁改口径，轮末统一回改 |
| workflow fail-fast | datus q09（原 B4）31 次 SQL 后试图 bash 写临时文件 → PERMISSION_DENIED 中断无答案 | 复跑加 `--execution-mode interactive`（配自动应答）或题面限定口径 |
| 假一致 | 同库同脏 + 口径巧合同值 | Step 1 口径对齐强制先行；有 T1 基准的题优先对基准 |
| 题面歧义传染 | cube ask 反问说明题目本身含糊 | ask 记录进报告；下一轮出题消除歧义（模板题带明确口径限定） |
| 静默选口径 | datus 无 ask 机制，歧义题会自己拍板 | 口径必须可从作答卡 sql/查询参数追溯（散文不落卡，D14）；裁判发现无法追溯口径的题降级为"待复核" |

## 二、datus 调用方式

### 2.1 单题调用

datus 经 **chat API** 调用（`datus --web` 常驻服务，与 UI 同源，默认 `:8501`）：

```bash
# POST SSE 流：message 事件内层 payload 即 MessagePayload（提取规格见 §2.2）；
# 每问新 session_id（题间零污染）；agent 配置/语义模型只在服务启动时装一次；
# subagent_id 为路由字段：ask_metrics=指标问答节点（query_metrics 通道），缺省=默认 chat 节点。
curl -N -X POST http://localhost:8501/api/v1/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"message":"2022年全年非税缴款金额和笔数是多少？","session_id":"probe-001","max_turns":30,"subagent_id":"ask_metrics"}'
```

- 每问新 `session_id`，会话互不污染；单题十几秒量级；墙钟上限单题 3 分钟，到点截断留证（作答卡 status=timeout，D10 六值）。
- **全题指标优先（D13）**：每题先走 `ask_metrics` 节点——`query_metrics` 交 dosi 引擎按语义模型编译 SQL（口径保真，`metrics_hit` 由此有值），无最终答案（未建模/报错/超时）降级默认节点再答（表达力兜底），两级尝试全留痕（meta.routes）。路由不读题型：题型是出题人侧考纲信息，答题人不读（盲考）。
- 数据源用项目 `.datus/config.yml` 的 `default_datasource: yunnan0508`；权限档默认放行只读（与 UI 同款）。

### 2.2 输出解析规则（作答卡的提取源）

| 要提取 | 来源 |
|---|---|
| 生成的 SQL | `call-tool` 中 `toolName=execute_sql` 的 `toolParams.sql`；指标路径的 `query_metrics` 返回体不含 SQL（工具层防 LLM 上下文膨胀而剥离），走**执行记录取证**（见下） |
| 命中指标 | `query_metrics` 的 `toolParams.metrics/dimensions/time_*` 与返回行；`search_metrics`/`get_metric` 的参数与结果 |
| SQL/指标执行结果 | 对应 `call-tool-result` 的 `result.result.data.compressed_data`（CSV） |
| 最终答案（散文，仅留痕） | depth-0 的 assistant `markdown` 内容——只存 `runs/` 留痕（`raw_path` 指认），不落卡 |
| 答案值行（D14） | 提取步 LLM 把散文结构化为值行：只抄数不推算，`metric` 取指标登记表（无则标 `未登记:<名>`），`unit` 必填 |
| 真实错误码 | FuncToolResult 的 **`error` 字段**（正文文本里的 "Code NNN" 是 KB 文档内容，误报源，勿用正则扫全文） |

提取规则的实战出处：v0 25 题人工实测（datus 仓 09 号文档）。按独立适配器重写为 `ask_datus`（见 [implementation.md](implementation.md) 答题人适配器一节），本表即其提取规格。

执行记录取证（v4，2026-10-23）：query_metrics 实际执行的 SQL 原文由 datus 侧日志留痕（dosi/runtime.py 在 `engine.execute` 成功后记 `dosi_sql_executed` 行——旁路观测，不改返回值与 LLM 所见），`adapters/ask_datus/evidence.py` 按题时间窗（meta.routes 的 started_at/ended_at）提取进作答卡；取证失败降级 sql=""，不影响作答与状态。不采用改返回体的方案——那会令 LLM 每次调用多背数万字符 SQL 且扰动答题人行为基线。

### 2.3 批量驱动

由适配器 `ask_datus` 驱动：读本工作区 `rounds/<轮>/questions.jsonl`，逐题经 §2.1 通道作答后按 §2.2 规格提取，写 `answers/datus/qNN.json`（含原始 payload 留痕）。题库外置，不改脚本内列表。

### 2.4 权限与执行模式

| 场景 | 做法 |
|---|---|
| 只读 SELECT | 默认权限档自动放行（与 UI 同款） |
| 需要放行写操作/bash | 请求体加 `"permission_mode":"auto"`（normal/auto/dangerous 三档，按请求覆盖） |

### 2.5 首轮实测摘要

25 题：24 成功 / 1 中断（q09）；0 真实运行错误；总耗时约 64 分钟。对账结论与遗留问题见 datus 仓库 09-datus-票据链路问数实测记录；07 号清单基准的三处标注/口径疑点（q01 全库口径混标、q21 划拨重复计数、q24 欠缴口径）已由该轮暴露。

## 三、cube 调用方式

### 3.1 调用链

```
POST http://localhost:4100/chat {question, sessionId}     ← 自然语言问数唯一入口（agent-svc）
   └─ Claude Agent SDK + cube-ask skill                    ← NL理解→构建Cube query→执行→成文
       └─ POST :4000/agent/query {query}                   ← 语义查询执行（agent-api 挂载件）
           └─ POST /cubejs-api/v1/load                     ← Cube 网关 → ClickHouse yunnan0508
```

分层纪律（agent-svc 设计约束）：问数知识零存在于服务层——编排循环在 SDK 引擎，表达契约在 `chat/cube-ask/SKILL.md`，数据真相在 `:4000/agent/*`。

### 3.2 POST /chat 契约与三态

```bash
curl -s http://localhost:4100/chat \
  -H "Content-Type: application/json" \
  -d '{"question":"按执收单位统计未到账的缴款笔数","sessionId":"batch-01"}'
```

返回三态 JSON，批量驱动按 type 分流：

| type | 含义 | 互搏批量的处理 |
|---|---|---|
| `answer` | 有答案（含口径说明/表格） | 提取值行落卡（散文留 runs/，D14） |
| `ask` | 歧义反问（question + options） | 记录反问本身（歧义信号）；按固定拍板政策用**同一 sessionId** 追问（如"按 A 口径"）续会话拿 answer——q10 欠缴口径拍板即此模式；q25 清分率比值的拍板记录在 09-cube 文档 |
| `nomatch` | 答不了（gaps） | 落为**建模缺口**记录；归因时现查语义层——语义层有相关指标而 nomatch=执行/配置事故；两侧均 nomatch=双侧共同缺口 |

`sessionId` 相同 = 续同一会话（SDK resume）；每题独立 sessionId，拍板追问时复用。

### 3.3 启动与依赖

- 启动：`D:\develop\cube\start.cmd`（幂等：Cube 走 docker compose；agent-svc 探到 :4100 已监听则跳过）。
- 依赖：宿主机 `claude` CLI（agent-svc 每题 spawn 一轮 SDK 会话，超时 600s，`AGENT_SVC_TIMEOUT_MS` 可调）。
- 留痕：`logs/agent-svc-YYYY-MM-DD.log` 全程记录 thinking/tool_use/tool_result 逐块，直接可作互搏的审计档案。
- 性能预期：每题完整 agent 循环，单题 20s~2min+。

### 3.4 数据源核实

`.env`：默认源 **CUBEJS_DB_TYPE=clickhouse / 172.18.166.126:8123 / yunnan0508**——与 datus 同库，数值互证成立。Oracle yn0411（172.18.163.68）为旧默认源，工作树模型已删、仅保连接。

### 3.5 与 regress/run_yoy.py 的区分

`cube/regress/run_yoy.py` 是**语义查询回归**（发 Cube query JSON 对锚点数字比对，含 continueWait 轮询与 Decimal 容差规则），不是 NL 问数。互搏闭环题（feedback.md 闭环行）积累成熟后，其"拍板口径"应下沉为该脚本的 query 用例——两层回归互补：问数层（互搏复验集）保语义表达，查询层（run_yoy）保模型编译。

### 3.6 首轮实测摘要

同 25 题 + 5 道缺口验证题（q26-q30）：q01-q25 中 nomatch 2 题（q07 单位树、q09 非叶子单位）、ask 拍板 1 题（q25 清分率比值）；q26-q30 中 3 题预期 nomatch 实际可答（q26-q28）、q29 ask 拍板后可答、q30 nomatch（预期达成）。逐题答案、query JSON、编译 SQL 见 datus 仓库 09-cube-票据链路问数实测记录；与 datus 的逐题对照见 datus 仓库 10-票据链路问数对账（datus-vs-cube）。

## 四、一轮互搏的执行清单（SOP）

1. **出题**：编制考纲（原始资料收编为业务课本 business.md，剥题纪律）→ 出题人**只读考纲**出 questions.jsonl（题型问数族 5 型见 §1.5，标 syllabus_ref，出覆盖矩阵；不读答题人侧产出、不标预期）。
2. **答题**：datus 走 `ask_datus` 适配器、cube 走 `ask_cube` 适配器（各自读 questions.jsonl，写统一作答卡；ask 按固定政策追问）。双方原始留痕归档 runs/。
3. **作答卡提取**：双方答案 → 统一作答卡 JSON：值行数组为答案唯一载体（提取步 LLM 结构化；散文不落卡，全文在 runs/ 留痕，D14）。
4. **裁决**：裁判（Claude，带两侧语义层定义切片）逐题出 verdict：互证通过 / 建模差异 / 执行事故 / 待人工；分歧题产出修正答案。
5. **对账文档·轮报（轮到此为止，系统段结束）**：report.md——四指标 + 分歧明细（沿用 10 号文档纪律：只陈述客观差异）+ 复验集（D6）。
6. **回改①②③（人调起智能体+人）**：①人看过分歧明细后调起智能体，codeqa 逐题查真实字段解法（过滤器+指标+维度+时间锚），由智能体**创建回改单 feedback.md**（文件头契约+主表+回改卡；查完的行=草案，未查的行登记待查证）；②人逐行审定；③人按回改卡改双侧语义层+清记忆，拍板结论落 YAML/词典，"已裁定口径"粘贴进课本。
7. **回改④⑤（复验+闭环）**：`bin/round.py --retest` 一条命令自动（清记忆→重启两服务→原题重跑到轮报）→ 挂了回③、口径错回①；通过且人工确认后 feedback.md 行状态置闭环（无独立套件文件）。
